# 空間構成のクロスレビュー

2026-10-31。対象は `tidewater_design.py` と `kelpline_design.py` が返す隔離座標モデル。Tidewater は別の設計担当の案をレビューした。レビュー担当自身が Kelpline の座標設計を担当したため、Kelpline の本書を独立した第三者承認とは呼ばない。独立コードによる別検算は [`independent_validate.py`](independent_validate.py) と [`independent-review.md`](independent-review.md) を参照する。

## 前案から解消した問題

[`../map2/height-audit.md`](../map2/height-audit.md) では Tidewater の下層の約 82% が y=0 と y=1.2 に集まり、遷移が全幅の Z 帯だった。Kelpline は下層 10,152 WU² がすべて y=0 で、上層も一つの y=3.2 に集まった。平面の壁や切り欠きの追加と、床自体の立体化を区別する必要があった。

今回の Tidewater は、中央へ下りる公共広場、西側の市場上階と下の街路、東側の中間段丘と展望床という異なる断面を持つ。Kelpline は、中央の乗船デッキとその下のサービス街路、側面の高い乗換回廊と低い岸壁、反対側の荷役場とフェリー指状岸壁を組み合わせる。どちらも床の高さを局所でつなぎ、全幅を一斉に上げる帯を繰り返していない。

床高の比率を均すこと自体を本家の基準にはしていない。この計画で「箱の上面を数えて多層に見せる」「一つの高さの大床へ戻る」ことを検出するための指標である。階段一段や坂の中間高さ、遮蔽物の上面を水平床の高度数に入れていない。

## 座標モデルから確認した数値

共有検算 `geometry.validate(build())` を直接再実行した値。床の支持・通路幅・ルール物の実挙動をゲームで測った値ではない。

| 項目 | Tidewater | Kelpline |
|---|---:|---:|
| 水平床 / 坂 / 障害物の部材数 | 39 / 28 / 22 | 42 / 22 / 19 |
| 真に滞在する水平床高の数 | 5 | 6 |
| 最大の水平実床高度比率 | 21.8495% | 26.9837% |
| 正確な矩形分割による正味投影和集合 | 7,874.4 WU² | 8,887.2 WU² |
| 通行床が上下に重なる XZ 面積 | 352 WU² | 2,208 WU² |
| その上下での最小静的空き高さ | 4.2 WU | 3.0 WU |
| 床・坂の共有辺から作った接続辺数 | 82 | 82 |
| 接続成分の数 | 1 | 1 |
| 最小の坂幅 / 最大勾配 | 4 WU / 45% | 4 WU / 45% |
| 全指定ポリラインの静的サンプル失敗 | 0 | 0 |
| 現行専用検査でのヤグラサンプル失敗 | 0 | 0 |

Tidewater の上下投影重複は正味投影面積の約 4.47%、Kelpline は約 24.84%。Tidewater を「前案より上下重複が増えた」とは説明しない。前案の上限値と今回の障害物控除後の値は条件も違う。本案の Tidewater の主な立体性は、広い床そのものの五高度と局所接続にあり、真正の上下通路は市場付近に集中する。Kelpline は上下の二つの交通をより広い面積で交差させる。この違いは両ステージの構造の違いとして維持した。

## 経路選択の追加検算

共有辺グラフを入力に、各部材ノードを `in → out` に分け、内部ノード容量 1、出発・到着ノード容量無制限として最大フローを計算した。これにより、単に「全体がつながる」だけでなく、中間の床・坂ノードを共用しない経路がいくつあるかを確認した。

| 出発 → 到着 | 中間部材を共用しない経路数 |
|---|---:|
| Tidewater `A_spawn` → `C_basin` | 3 |
| Kelpline `A_spawn` → `central_solid` | 2 |
| Kelpline `A_spawn` → `central_service` | 2 |

これはグラフ上の条件である。大きい一枚の床を一つのノードに扱うため、床内部の局所遮蔽や武器の制圧範囲を表せない。指定されたポリラインの身体半径付きサンプルと併読する。Tidewater の低い市場街路は主経路の下層広場から分かれる枝であり、別のスポーン出発経路という意味ではない。Kelpline の四つの行程例も、全区間独立した四レーンという意味ではない。

## 落下と復帰を修正した点

Kelpline の最初の中央金網案は、低い床に安全に着地しても、指定復帰が約 81 WU 必要だった。これは単に「復帰可能」と記載して残すには過度な遠回りである。金網を既存の局所復帰坂の隣へ移し、中央のルール目標橋は実床にした。最終案では金網着地から上層へ 37.77 WU、バルコニーの縁からの着地は 28.27 WU の指定経路を持つ。復帰のためだけに水を埋めたり、床を貫通する移動を置いたりしていない。

Tidewater の金網・橋端落下は、市場下の街路から別の上り坂へ戻る構成である。橋の縁からの降下は上床の外へ移動してから落ちる。静的図面の開始点と着地点を結ぶ線をそのまま身体の放物線と解釈しない。落下中の横移動、慣性、硬着地、イカの姿勢、頭上カメラは別の受入試験である。

## 接合とルールについての判定範囲

正面積で同じ床を重ねる処理と、床下を通れないほど低い上床の重複を設計段階で除いた。Kelpline の初稿には後方コンコースの基礎と低岸壁の食い込み、および高回廊との 0.6 WU しかない隙間があったが、コンコースの実際の端を切り、横坂の終端を移して解消した。通路線の端ぎりぎりの曲がりも床の内側へ修正した。検査器の閾値を緩めて通したものではない。

ルール候補は支持床のある位置へ置き、エリアの矩形は上下の別の実床と重ねていない。ヤグラについては中心線だけで済ませず、ソースを踏まえた床・柱の形と旋回時の隅を共有検査器で確認する。生成された最終監査の条件が正である。実ゲームの最高床検索、移動物の更新順序、搭乗者、得点、床の塗りへの干渉までは、このブロックアウトで確認していない。

## 残る具体的な設計・実装リスク

- **坂の生成方式。** 隔離モデルは矩形内の平面坂だが、公開版の `Level.R` は下端の延長や法線方向の厚みを持つ。今回の隙間・接触面をそのまま既存ヘルパーで作れるとは限らない。実 OBB と隣接体積を再検算する必要がある。
- **カメラ。** 空き高さ 3.0 / 4.2 は身体を置く余地を確保する。1.85 のピボット、長い後方ブーム、半径 0.62 のプローブを含めた旋回・後退・壁際画角の快適さを保証しない。
- **上下の UI と AI。** 各面の塗りは区別できても、最高面中心のミニマップとナビの上下ノードは別の問題。下層を見落とす UI や経路選択を解消してから本体へ統合する。
- **射線と武器差。** 独立検査は有限個の幾何学的な直線を示す。射程、弾速、曲射、爆風、塗り、反応時間、復帰圧を含む対戦検証ではない。幅・高さ・遮蔽が機能するかは短射程と長射程の両方で確認する。
- **水際の読み取り。** 水は実際の床がない部分に残す。柵や縁の色を追加するときに、坂幅・射線・落下口を新たに塞がないことを再検査する。

この段階の合格は、二つの異なる立体構成が座標と図に矛盾なく表れ、代表的な経路とルール候補の静的な成立条件を満たしたという範囲に限る。実ゲーム・本家実機・対戦の検証済みを意味しない。
