# 次のエージェントへの設計依頼

あなたは INKWAVE のレベルデザイナーです。`AGENTS.md` に従い、公開版 `inkwave-public/` の通常ステージ Tidewater Plaza と Kelpline Terminal を再設計してください。港のネイティブステージは変更対象外です。

目的は、大きいだけの平坦な床に遮蔽物を置く案や、2階を一律の高さで足す案から抜け出し、本家スプラトゥーン3のステージが持つ複雑さ、視認性、経路選択、攻防の変化を学んだ上で、両ステージ固有の立体的な地形を設計することです。原作ステージのコピーは求めません。

## まず現状と資料を調べる

- `docs/stage-redesign/` の前案、`docs/stage-redesign/map2/` の最新案と図、`height-audit.md` を読み、現行実装と案を混同しない。既存実装の大型化・装飾は途中段階であり、設計案の実装ではない。
- `inkwave-public/src/world/maps.js` と移動・衝突・塗り・カメラ・ルールの関係箇所を読み、ネイティブステージと対象2ステージのスポーン間距離、外接寸法、実際に算出できる床面積を同じ方法・単位で比較する。1 WU と m の対応が根拠を持つか確認し、仮定と実測を分ける。外接面積、水平面積、塗り可能面積、上下重複を混同しない。
- 本家の複数ステージを実際に上面図や動画等で確認し、出典、バージョン、観察した範囲を記録する。上面図から見えない高さ・移動可能性を断定しない。単なる見た目ではなく、地形の輪郭、エリアごとの幅や形の変化、高低差、上下関係、遮蔽、射線、分岐・合流、落下と復帰、攻防上の役割を観察し、どの設計判断に活かしたか説明する。

## 設計の条件

- 作業はまず既存ゲームと分離したディレクトリで行い、2ステージそれぞれの設計を完成させる。ゲーム本体のステージを置き換えない。必要な検証用ブロックアウトは分離して作る。
- ステージ全体の大きさはネイティブステージと同程度を目指す。ただし大きさを確保するために平坦な床を引き延ばしたり、水際を埋めたりしない。距離・面積の数値と算出条件を示し、未達や不確実性を隠さない。
- 立体性を飾りや箱の上面で代用しない。床そのものの複数の高さ、段丘、異なる高さ同士の接続、上下に重なる通路、見通し、地形の切れ目と水際を具体化する。各高低差が移動・射線・塗り・位置取りに与える意味を示す。特定の y 座標に面積が集中するだけ、またはステージ全幅が同時に段上がりするだけの設計を避ける。
- 中央、自陣、左右ルートそれぞれに地形上の役割と異なる選択肢を持たせ、単調な直線回廊や同幅の並列通路を避ける。一方、無意味な複雑化、行き止まりの乱用、視認性の悪化も避ける。両陣営の公平性を検討し、対応関係と例外を明記する。
- スポーンから中央と側面への経路、各上り・降り・合流・復帰、落水、階段や坂の勾配・幅・頭上高、遮蔽、金網の挙動を座標と接続関係で明示する。通行可能性が未実測の箇所は未検証として扱う。複数ルールの目標・経路との干渉も確認する。

## 成果物と検証

- 両ステージの同縮尺の2D平面図を、各高さ層が読み取れる形で作成する。水、床が上下に重なる箇所、金網、障害物、坂・階段、経路、スポーンを区別し、断面図と高さを含む接続図を添える。図と座標表を一致させる。
- 高さ別床面積と、その計算方法、上層と下層の同一 XZ における重なり、各高度の配置位置、スポーン間距離を示し、高さの偏りを検証する。数値は目的に応じて選び、架空の本家基準値を作らない。
- 主要経路の到達可能性、床・階段の接合、衝突、塗装、カメラ、射線、AI、ルール物、両陣営の公平性を確認する。静的図面・計算、分離ブロックアウト、実ゲーム、本家実機の各検証レベルを区別する。検証できなかった項目は具体的に記載する。
- 最終報告には、観察した本家の設計上の特徴、両ステージごとの新たな構造、寸法と面積、図へのリンク、検証結果、残る問題を含める。完成と断言する前に、単調さと y 偏重を自分で再評価する。
