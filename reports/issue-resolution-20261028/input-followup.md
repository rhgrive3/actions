## Reference and scope

The comparison target remains Splatoon 3 Ver. 11.3.0. The documented options expose separate −5…+5 right-stick and motion-control settings for TV/Tabletop and handheld profiles. Public option documentation does not supply the right-stick transfer curve. A third-party controller-bridge footnote reports approximate gyro output:input ratios of 1:1, 1.8:1 and 3:1 at minimum, default and maximum; its game version and measurement procedure are unspecified. `patches/splatoon3/reference/curated-numbers.json` therefore keeps `camera.gyro` unknown. Neither the bridge nor an INKWAVE synthetic trace establishes equivalence to current retail behavior. The user explicitly waived physical-device testing for this task; its absence is not a completion gate. Source-curve provenance remains a separate unresolved question.

## #287: stick profile and yaw boundaries

Before this follow-up, legacy multiplier 0.2 migrated to the new scale endpoint −5 and became 0.5×; 3 migrated to +5 and became 2×. The one-time migration now retains each profile's valid out-of-range legacy gain until its stick slider is edited or the settings are reset. It survives unrelated changes, profile switches and reloads. The tooltip explains this behavior. A legacy value that a previous version already clipped and saved is irrecoverable from the resulting save.

The existing provisional gain remains `2^(setting/5)`. Full-stick yaw previously made +4.5 and +5 identical at the existing `2π−1e−6` rad/s ceiling. INKWAVE now preserves yaw through +4 and maps the remaining interval monotonically into the same ceiling. This small upper-range interpolation is an INKWAVE consistency choice, not a measured Nintendo curve. The previous cap also applies to legacy gains above it, so retaining a 3× gain preserves pitch and the already-capped yaw rather than creating 3× yaw. Stick dead zones and gyro axis ownership were not recalibrated.

Production-composed source checks passed 52/52 including neighboring gyro and profile checks; actual emitted controller tests passed 7/7. The two added boundary regressions failed the old source and passed the candidate. Chromium settings UI checks passed at three viewports with trusted interactions and zero page errors. These checks do not establish Nintendo turn speeds. [#287](https://github.com/rhgrive3/actions/issues/287) retains a source-calibration gap: the retail right-stick curve is not available in the pinned source and the implemented mapping is provisional. Physical-device measurement is waived for this task; it is not being requested as an acceptance gate.

## Pointer-lock recovery

Native Chromium 154.0.8037.57 on this host rejected the raw request promise with `NotSupportedError` before delivering its unscoped `pointerlockerror` event. The old recovery gate required that event before the rejection and therefore did not retry in this ordering. A current exact request's rejection now permits at most one plain request only while the same input/match/flow/document owner is live and user activation, focus and visibility remain valid. Blur or hidden state cancels pending recovery, including after focus returns. Document error events cannot themselves authorize a retry; they carry no request identity.

The two new source counterexamples failed before the correction. Source and emitted pointer recovery each passed 40/40, the neighboring touch-pointerlock tests 34/34, and constructor/lifecycle checks 3/3. A real Chromium test of emitted Input with a controlled match owner acquired DOM lock three times: first through raw rejection and plain fallback, then twice with one plain request each. WebKit 26.5 reached the plain fallback but headless WebKit rejected it with `WrongDocumentError`; WebKit lock ownership is not established.

A separate earlier full-game charge test remains a failure: after a trusted Range entry and first successful full charge, the next real lock was acquired but the second charge reached 0.989 before the unchanged 15-second limit. Its receipt is `/workspace/scratch/input-pointer-native-game/result.json`; it is not a pass, and its full-charge assertion has not been changed. The dedicated pointer-ownership browser test is `scripts/check-inkwave-pointer-ownership-browser.mjs`; it tests normal trusted menu/keyboard paths and lock ownership, without charge completion, frame stepping or engine-state mutation. The single requested full-game 6-cycle run failed at initial ownership and completed zero cycles: trusted main → mode → Range succeeded with the same playing match and no page errors, but a normal canvas click left DOM and Input lock false after 45 seconds. The [raw receipt](pointer-fullgame-input.json) identifies the exact build, settings and failure. Its `failure.state.pointerErrors` is 1; the top-level counter remains its initialized zero on the failure path and is not the observed count. Source inspection shows that ordinary KBM canvas clicks only request lock under the existing `_relock` condition or the separate touch-handoff path; the harness incorrectly assumed an arbitrary canvas click would request lock before starting its Escape → Resume cycle. `Game.resume()` is a separate lock-request path. The result is neither six-cycle acceptance nor proof of a product reacquisition defect; it was not retried.

The scope hold recorded for PR #1907's MOV-08b remains in force; this follow-up is not authorization to merge that PR, change #401 or close either calibration issue.
