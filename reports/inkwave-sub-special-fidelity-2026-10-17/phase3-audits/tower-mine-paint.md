# Phase 3: moving Tower Mine paint admission

Reference: Splatoon 3 versus 11.3.0, GP0 baseline. Implementation audit/test date: 2026-10-17. No Switch video comparison or retail stage-coordinate parity was performed.

## Public behavior and existing geometry

- Current community source actually opened: <https://wikiwiki.jp/splatoon3mix/バンカラマッチ指南/ガチヤグラ指南>, sub section lines496–504. It states that placing a Mine on the Tower damages/marks an enemy rider, and that the player must themselves ride the Tower to place it there. It also discusses placing two Mines depending on Sub Power Up. This establishes a device attached to the moving Tower rather than a fixed launch-world-coordinate Mine.
- <https://wikiwiki.jp/splatoon3mix/ブキ/サブウェポン/トラップ>, lines60–64: place only at the feet while grounded; no second Mine in an existing sensor circle; third placement detonates the oldest. Line82 says an already placed Mine survives its owner's death. Lines88–90 document the small placement footprint separately from the later explosion.
- Geometry is the existing public INKWAVE ranked Tower blockout in `patches/splatoon3/runtime/ranked/world.mjs`, not extracted retail Tower dimensions. Deck center is path topY minus.12, halfY=.12, width/length half extent is clamp(stage.tower.halfSize,.8,1.4), and axes follow the horizontal path segment. The helper recomputes these from the immutable stage path and accepted host progress; it does not trust sender-submitted world pose or snapshot.rule.position alone. A contradictory position/progress snapshot cannot authorize paint.

## Implementation and contract

- New `patches/network-replication/tower-paint-support.mjs`: pure network helper, no all-subs import/cycle. Holds at most256 accepted canonical Tower poses per NetMatch. Scope includes match instance, ranked engine instance, cfg.id epoch and current host ID. Explicit host handoff/dispose clears the scope. No user-submitted pose is added to history.
- `ranked/network.mjs` records only successful current-host snapshot acceptance and actual local-host snapshot sends. Duplicates do not replace a revision; older/out-of-order snapshots cannot repopulate evicted revisions. Local host physics runs60Hz whereas ordinary objective snapshots run5Hz. `mineTowerPaintReference` publishes a genuine `rkstate` before birth/core when its current revision has not yet been sent. Actual collider must agree with the canonical pose. Follower geometry is normally synchronized directly from accepted state by RankedWorld beforeActors/update; any prediction/interpolation mismatch explicitly fails closed.
- Birth payload: `{support:1,supportRevision,supportX,supportY,supportZ}`. XYZ is the fixed deck-local feet offset. Birth must be on the deck footprint, near its top, have zero Mine launch velocity, and match that host pose's transformed world position within existing wire precision. Support is only admitted for `inkMine`.
- Core metadata: `[SUB_PAINT_TAG,epoch,nid,life,birthSequence,burstIndex,currentSupportRevision]`. Receiver transforms the original fixed offset using the referenced trusted pose, adds the existing raw-derived Mine paintOffsetY=.45, and requires the core center within.1. Radius remains exactly5; seed, shape, owner/member, causal sequence, source life, team and one-core checks are unchanged. Normal/static Mine, Burst and Fizzy remain six-field metadata and retain their prior checks.
- `research_subs` owns the actual all-subs attachment/birth/core integration. Mine feet remain the deck top; no+.02 deployment lift is applied. Spawn reference is captured before emitting the birth; current reference is taken before blast. A Tower proof failure never falls back to a static six-field grant. Local paint is preserved, while unproven wire paint receives no wider grant.
- `network-replication/adapter.mjs` adds the new helper to `networkIdentity`'s explicit hash list. Test-only robustness fixture adds opt-in `rankedNetwork:true`, since its production S3 installer does not itself install ranked mode.
- Final cross-peer ordering extension reuses the existing sender pending queue, MAX_PENDING256 and WAIT_SECONDS2. Unknown future host revisions defer the Mine birth/core and following sender rows without granting a capability. An accepted genuine host proof invokes a small helper listener, then the existing prepare/register/receipt and `_queueKitRecoveredEvents` path revalidates and consumes. Original envelope ts/u-ineligible rows are removed before any ready/pending merge, and the merge also requires a retained eligibility WeakSet entry; a context-free playback retry cannot upgrade a rejected row. A WeakMap fixes each pending birth's original host scope. Deadline or handoff retires the blocked claim before retry, even if the late proof is already known; it cannot resurrect on a newer sequence. Known-evicted/past-missing revisions never gain a waiting exemption.

## Explicit limits / not parity claims

- Reliable ordering is per peer connection. Normal host-proof-after-Mine ordering now recovers when the authentic referenced revision arrives within the existing sender queue's2s window and256-row limit. A proof arriving after the deadline, a queue over capacity, or a past revision that is absent/evicted still rejects the wider paint. The bounded deadline is a network validation policy, not a measured retail gameplay duration.
- History is bounded at256 unique host revisions (ordinary5Hz gives roughly51s, extra Mine publication can shorten this). An already accepted birth keeps its fixed offset when its birth pose is evicted, but a core referring to an evicted pose is rejected. Delayed first births also require their pose still present.
- Host handoff intentionally invalidates outstanding old-generation Tower Mine paint capabilities, including when the same host ID later returns. Existing Mines may keep local gameplay/paint, but a future authenticated rebind protocol would be needed to authorize their wider remote paint after handoff. A peer's claimed free pose cannot perform that rebind.
- Only canonical ranked Tower deck attachments are admitted. Other moving custom platforms, crush/destruction behavior and retail stage geometry remain outside this change. The.011 birth and.1 core tolerances are wire validation bounds, not measured Splatoon distances.
