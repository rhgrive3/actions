# CPU comparison baseline validation (2026-10-29)

At source `2b01cd7efbca260a611165b1e3887ff48062ccd5`, the separate `compare-inkwave-composed-cpu.mjs` accepted `status: passed` reports even if the first/baseline scenario recorded a lost GL context or a page error. It checked those fields only for the repeat and candidate. It also accepted three empty scenario arrays, returning an empty list. These are malformed/contradictory inputs: the capture runner itself ordinarily marks those conditions failed, and no historical performance result was shown to suffer from them. A caller comparing an altered or incomplete result, however, could mistake the returned comparison for a valid measured workload.

The comparator now requires every input to contain at least one scenario and requires every scenario, including the first baseline, to report `contextLost: false` and no page errors. Existing scenario, environment, identity, gameplay, resource, draw and BVH comparison policies remain intact. No timing threshold, field mask, workload, product runtime or GPU was changed. The independently defined #1434 strict native/native pixel and upload-version gate is unaffected.

Three new negative controls reproduce the old omissions: the [pre-change output](before.tap.gz) fails each assertion because the invalid baseline or empty comparison was accepted. The [fixed output](fixed.tap.gz) passes all five comparator tests. The comparator also re-read the previously recorded A1/A2/B1 source receipts from [the retained CPU continuation evidence](../../issue-resolution-20261028/cpu-continuation/README.md) and retained their existing [exact recorded-state comparison](historical-comparison.json); no timing or FPS improvement follows from that comparison. Those earlier CPU observations are legacy Tidewater without final scene rendering, not a calibrated whole-game render benchmark. The native/native 134/135 upload-history preflight remains rejected.

Reproduce the tests with `node --test scripts/tests/inkwave-composed-cpu-comparison.test.mjs`. The negative receipt is the same tests against the unchanged pre-fix comparator; it is not a claimed production-runtime failure.
