# 2026-10-25 テイオウイカ・照準・SP増加調査

対象はユーザー報告 5・6・16。作業開始点は `7f863ea2d65671abd1453fdae1b61de00f1d10e2`。公開版の合成ソースを用い、別の `game/` 試作は比較対象にしていない。

## 5. テイオウイカ

比較はスプラトゥーン3 Ver.11.3.0、スペシャル性能アップ 0 AP、通常床・塗れない床・自インクの壁、ZRの押し続け／解除、ジャンプ攻撃中のチャージ。

数値の一次参照は公開抽出者 Leanny の [WeaponSpCastle 11.3.0](https://raw.githubusercontent.com/Leanny/splat3/7280ff9cde8bb1c5dcef46c700c326471584d2e6/data/parameter/1130/weapon/WeaponSpCastle.game__GameParameterTable.json)。取得したパラメーターを `patches/splatoon3/reference/kraken-input-surfaces-1130.json` に記録した。任天堂が公布した仕様書とは区別する。

| 確認した実装上の原因 | 修正と再現条件 | 確認状態 |
| --- | --- | --- |
| ジャンプ攻撃の当たり判定が `rt.v0` にある照準方向を座標で上書きする | 発動状態に独立した照準ベクトルを保持。空中でZRを押し、開始位置を `(14,0,-23)` などへ変えてもカメラの水平照準方向を維持する | 実Actor・実Specialの回帰で確認 |
| ZRを押したフレームのチャージ時間が0で、35Fの保持が34Fになる | 押下を含めて時間を進める。34F解除はキャンセル、35F解除はダッシュ | 30／60／120 Hzと不均一な間隔で確認 |
| 変身中に押し続けたZRの押下エッジが失われる | 操作可能になったときに保持入力を受理。変身後に押し直す必要をなくす | 実Specialの回帰で確認。プラットフォーム入力キャンセルも既存テストで確認 |
| 床も壁も通常床のダッシュ速度を使い、壁では通常イカの登り速度・移動スティックに戻る | `Dash_MoveSpeed_Floor_NoPaint=.21` と `Dash_MoveSpeed_Wall_MaxCharge=.22` を接続。通常床 `.3` と区別し、ダッシュ中の壁接着は固定した進行方向を使う。上向きの壁移動に当たり判定の前方オフセットも揃える | 実Level・実Physics・実Actorの床／壁で30／60／120 Hzを確認 |
| 時間の浮動小数誤差で終了表示と無敵終了がずれる | 変身／終了の判定と被ダメージ側の境界許容値を統一。480Fで回復動作に入った後に無敵が1F残る症状を解消 | 終了フレームの実damage経路で確認 |

時間と距離の橋渡しは既存のものを使用した。速度はソース値×60で、通常床18、塗れない床12.6、壁13.2 INKWAVE単位/秒。これらは任天堂のメートル単位の実測ではない。塗れる乾いた床は通常床として扱い、接地面が塗れないときだけ低速側を使う。

継続時間は変更していない。[検証Wikiの動作記録](https://wikiwiki.jp/splatoon3mix/ブキ/スペシャルウェポン/テイオウイカ)は、0 APの480Fが変身60Fを含み、その後に通常イカで移動できる60Fの回復があると記録している。今回もこの区切りを維持し、回復中に通常イカで移動できること、ジャンプできないこと、被ダメージが有効なことを検査した。この入力・状態の記録と、上記の抽出数値は根拠の種類が異なる。

未確認：壁の縁とインク境界での完全な実機軌跡、加減速曲線、`Dash_InvalidFrame` の詳細な意味、ノックバック、イカロール／イカノボリ、ボム接触、隠れ状態、スーパージャンプの着地点など。今回の修正でテイオウイカ全体を本家と同等と判定していない。

## 16. 照準の大きさ

既存のシューター照準は任天堂の1280×720画面を基準に、縦の半幅24px、線幅3px、長さ14pxで校正されていた。参考画像と測定方法は `patches/splatoon3/reference/shooter-reticle-reference.json`。これを低い画面にも固定CSSピクセルのまま出していたため、390px高の横向き端末では画面に占める比率が720px高の約1.85倍になっていた。

照準・ヒット表示・キル表示の図形に、`min(1, max(0.5, viewportHeight / 720))` の表示倍率を適用した。下限0.5は小さい画面で線を残すためのINKWAVEの表示上の選択であり、本家の計測値ではない。720px以上の高さでは拡大しない。既存の7表示系統へ全カタログが割り当てられるため、追加ブキもこの共通表示経路を通る。

弾道から投影された座標と図形の大きさは別の量である。照準中心とヒット表示の移動量はそのまま保ち、発散幅、マニューバーの左右着弾点、チャージャーの現在／最大射程の表示点は表示倍率の逆数で補正した。タンクやボム消費表示の親全体は縮小していない。リサイズ時には変更のない発散幅も再描画し、古い倍率が残らないようにした。

## 6. スペシャルゲージの増加

この担当の調査では、`PaintSystem.splat → Actor.addTurf` が新規所有した床の生のワールド面積をそのままSPポイントとして加算していることを確認した。時間による一括の増加倍率は存在しない。`source-distance.mjs` の現在の橋渡しはS3ソース1単位＝ワールド1単位、射程線1本＝5単位。

既存の `paint-raw-area-credit` と `issue-264-paint-score-boundaries` を合成済み実Actor・実PaintSystemで再実行し、同色の重ね塗りが二重加点しないこと、塗りの成長と本体で重複しないこと、壁や埋まった床を除外すること、スペシャル使用中の再充填禁止を確認した。ギア更新も基礎コストを復元してからSP増加量の補正を一度適用しており、再装備による累積除算は確認されなかった。

S3の面積→p換算そのものの一次根拠はこの時点で未確定。初代の検証投稿、Garry's Modの移植コード、SplatNet2の面積表示をS3の確定係数に置き換えていない。Driveの公開ソース資料Part01の出典はDexx-ioのアセット、Leanny/splat3、HoianViewer等であり、SPの面積換算を確定できる実行ロジックの逆コンパイル資料ではなかった。今回のコミットは根拠のない全体倍率を追加しない。親の統合調査で、この課題を続けて扱う。

## 検証と既存テストの保守

新規の `kraken-input-surfaces-20261025.test.mjs` は16ケース通過。Special・ゲージ・塗り・照準・入力キャンセルの関連18テストファイルが最終的に通過した。`check-inkwave-patches.mjs --quick` と `git diff --check` も通過した。

初回の広域実行では既存の `kraken-jump-spin.test.mjs` だけが比較baselineの期待失敗数12と実際14の不一致で失敗した。`7f863ea2` と未変更VFXのSHA-256が一致し、親の未統合treeでも同じ失敗を確認した。原因は故障注入の削除範囲が、後から追加された共通の `const emissionTicks` 宣言まで消していたこと。このため本来は成功すべき非攻撃状態のテストも含め、全7ケースが `ReferenceError` で失敗していた。

削除範囲をジャンプ攻撃だけに戻し、期待どおりbaselineは source／production-transform とも1成功・6失敗、候補は双方7成功になった。期待する失敗6件をテスト名で明示し、単なる失敗総数の調整ではなく、故障注入が正しい欠落を検出していることを確かめた。候補の成功条件や故障注入そのものは緩めていない。
