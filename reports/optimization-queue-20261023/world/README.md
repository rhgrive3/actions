The active paint-capacity proposal is rejected with a reproducible GPU counterexample (`profile-paint-capacity.mjs`, `paint-capacity-desktop-profile.json`). The candidate changes only `MAX_QUADS` from 6000 to 1024. On a deterministic 256×256 atlas, counts 0/1/1023/1024 match; at 1025, 55,254 green/wetness channels differ by at most 2/255. Red, blue and alpha match. Disabling the drying pass produces zero differences for the same 1025 quads. `_drawQuads` draws drying before its current batch; extra early flushes therefore change which new splats are dried before the final batch. At 6000 quads the candidate causes six render/mipmap passes instead of one (warm median CPU submission 1.6 versus 1.2 ms); at 12000, twelve instead of two (2.7 versus 2.2 ms). The 1,393,280 logical byte saving does not justify this behavior change. These are desktop synthetic atlas diagnostics, not full-stage or iPad timings. No capacity change was shipped; a growth scheme preserving the original flush boundary would need separate peak-memory evidence because old and replacement GPU buffers can overlap.

The native source-mask proposal is rejected for the current mutable paint contract. `ranked/world.mjs` installs tower cells by extending `dead` with `.length`/`.set`, reads a `.subarray`, writes dynamic buried cells, then copies those cells back and restores the prior array. Those cells do not exist in `level.mask`. Scoring also keys its cached index by `dead` identity. Replacing all reads with an immutable source-mask lookup would omit live dynamic state; a proxy or destructive inversion is not adopted. A compatible lazy materialization/overlay would be a broader API migration with CPU and mode acceptance still to establish. Existing tower, coverage, scoring and source-cache checks pass (46 tests); unchanged production logic is intentional.

The incremental Git SHA-1 proposal is conditional on measured iPad CPU and RAM improvement. Browser WebCrypto exposes a single-input digest API; the repository has no vetted incremental browser SHA-1 implementation. The Node incremental oracle establishes hash equivalence, not browser performance. No device evidence supports introducing a new hasher. Exact byte-length and Git SHA-1 validation before cache/decode publication remain unchanged; the per-file concatenation allocation remains an acknowledged tradeoff rather than a claimed fix.
