# 原典ステージのインク描画を塗られたチャートに限定（2026-10-19）

開始 main: `3e8812d`。作業ブランチ: `ccr-273ec130-hszbwg`。原典ステージの GPU 負荷を、描画結果を変えずに下げる。

## 問題

インク重ね描画（`native-game-ink`）は、16 単位の描画領域のうち「塗りの範囲に触れた領域」と視錐台の両方を満たす三角形をすべて描いていた。領域に少しでも塗りが入ると、その中の未塗りのチャート（塗り atlas の平面区画）もレベル用の重いシェーダー（texlib・ノイズ・光源・影・波紋）で全画素を計算し、最後の `a < 0.015` の discard で捨てていた。試合が進むと大半の領域が「塗りあり」になり、実際に色を出す三角形はその一部だった。

## 変更

`patches/native-stages/runtime/native-ink-chunks.mjs` の `NativeInkMesh`：

- `bindPaint` で `paint.paintFaces`（atlas と三角形を持つもの）の順に、チャートごとの三角形範囲を作る。`nativeInkGeometry` はこの順にチャートの三角形を連続して出すため、合計三角形数がジオメトリと一致した場合だけ使う。一致しなければ従来の領域選択のまま。
- 既存の `_pushQuad` ラッパーで、クリップ後に面積が残った quad のチャートを「塗られた」と記録する。`_pushQuad` は quad をそのチャートの pad 付き atlas 矩形に切り詰めて書くので、一度も quad が来ていないチャートには atlas のインク texel が無い。
- 選択は「視錐台内の領域」かつ「塗られたチャート」の三角形を、元の三角形順で index に集める。透明合成の順序・材質・属性・ソート中心は変えない。
- 新しく塗られたチャートがあったときだけ index を作り直す。カメラが同じで塗りが増えていなければ再送しない。
- 失敗時は描画を減らさない方向に倒す：未登録のチャートへの書き込み、束縛時に塗り済みの atlas、`geometry` の差し替え（品質切替）では、チャート選択を外して従来の動作に戻る。`clear()` で記録を消す。
- `faceCulling = false` で従来の領域選択に戻せる（比較用）。

CPU の塗り・物理・ナビ・ルール、シェーダー、テクスチャ、表示メッシュは変えていない。ゲームの挙動は変わらないため、[挙動比較記録](inkwave-splatoon3-behavior-2026-10-02.md)に該当する差分はない。

クサヤの4視点で、同じモードを繰り返し描いても変わる画素が各8〜33画素あった（シーン全体のみ。インク単独では0）。これらはインクを消したシーンでも変わり（`unstableWithoutInk`）、比較から除外して別集計にしている。比較中はメッシュ以外も含めて全オブジェクトの `onBeforeRender` を止める。止めるのがメッシュだけだと、粒子などで揺れる画素が増えた。

通常の公開ビルド（原典をブラウザが直接取得する `browser-direct`）でもユノハナの対戦を開始し、チャート選択が束縛される（45,171チャート、10秒時点で可視領域内 21,747→431 三角形）ことを確認した。

既存の `scripts/check-inkwave-native-render.mjs`（領域分割前の1回の全域描画との比較、ユノハナ・クサヤ×3視点）も画素差0で通った。

時間は SwiftShader（CPU 上のソフトウェア GL）の中央値で、実 GPU・モバイル端末・Switch の描画時間ではない。三角形数と、同条件での相対差として扱う。「塗り」の6秒・60秒は通常の対戦進行、「合成」は `NATIVE_SYNTH_SPLATS=4000` で全チャートに散らした通常の splat（終盤の塗り分布の代用で、実際の試合の分布ではない）。

試していない・保証しないもの：

- 実機 GPU の時間、消費電力、発熱。
- 品質切替で `geometry` を作り直した後は、チャート選択も塗り領域の選択も外れ、視錐台だけの選択になる（変更前と同じ）。
- 塗りが広がる間は、新しいチャートが塗られるたびに index を作り直す（CPU は下記）。
- 「不採用にした案」の節に書いた atlas ミップのにじみが出る視点で、その画素が描かれなくなること。
- 確認したステージはユノハナ・クサヤの2つ。他の原典ステージでは、束縛の成立（チャート順と三角形数の一致）を CI の Node テストではなく、アセットを用意した環境でだけ確認できる。

同じ対戦をチャート選択あり・なしで別々に進め、毎フレーム `selectVisible(G.camera)` の時間と index の再送回数を測った（LOW、描画は省略し、カメラは試合の進行に従う。Chromium の JS 時間で端末の値ではない）。

## 不採用にした案

未塗りの 2×2 quad をシェーダーの先頭で discard する案も試した（`dFdx/dFdy` を分岐前に取り、近傍9点が閾値未満のときだけ捨てる）。画素差は0だったが、SwiftShader では discard で処理が省かれず、追加の texture 取得の分だけ遅くなる視点があった。実 GPU で効くかを確認できないため入れていない。

調査中、原典ステージの塗り atlas は JS 側で `minFilter=LinearFilter` にしているが、GL 上の `TEXTURE_MIN_FILTER` は `LINEAR_MIPMAP_LINEAR`（9987）のままであることを確認した（render target の sampler 設定は作成時に決まるため）。今回は変えていない。このため遠距離で粗いミップを標本化すると、atlas 上で隣にある別チャートのインクが未塗りチャートの画素へにじみ、late discard を通る可能性がある。チャート選択はそのような未塗りチャートを描かないので、にじみが見えていた画素は消える。今回の30条件ではそのような画素は0だったが、全視点での不在は確認していない（消えるのは本来のチャートに無いインクで、塗り判定・CPU の塗りとは無関係）。
