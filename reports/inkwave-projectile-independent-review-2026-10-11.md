## Initial findings

1. **P1 — Standard horizontal Roller never creates the intended liquid bridges.** `runtime/projectile-visuals.mjs::_rollerLinks` treats `fidelityRollerUnitIndex` as a per-glob adjacency index. The twelve native wide-swing globs all have source unit index zero; only the nearest unit has index one. The check `Math.abs(pi-qi)!==1` therefore discards every adjacent main-unit pair. A full composition, actual `Projectiles.fireFlick`, fixed random 0.5, two 60 Hz updates reproduced 13 bodies, 2,028 vertices, and `linkedRollerPairs=0`. Adjacent main heads were approximately 0.265 world units apart, inside the configured bridge interval of 0.18–0.9 at radius 0.3. This is a visible functional omission in the requested connected membrane.

2. **P2 — Coarse native update intervals mislabel history positions.** `recordStep` reads the final `p.prev` after `_step` returns. Native `InkFlightRuntime.stepHead` can execute multiple internal 60 Hz steps and overwrite `prev` on each. A real Shooter with `Projectiles.update(1/30)` recorded history age zero at z=2.565996 instead of its muzzle z=0.3; age 1/60 was z=3.698994 instead of the actual first endpoint z=2.565996; only the final age 2/60 endpoint z=4.831992 was correct. Menu-attract budgeting legitimately supplies coarse intervals. A history derived from the last segment is not a complete authoritative trajectory.

3. **P1 — The proposed long-firing browser performance capture measures a frozen game.** `scripts/check-inkwave-projectile-visuals.mjs::openGameContext` calls `g.debug.freeze()`, but the initial `runFiringPerformance` never unfreezes. Native `Game._loop` returns immediately while frozen. The independent rAF sampler can produce timestamps even while game-frame/projectile/render sample arrays remain empty. The harness initially had no nonzero native frame/shot assertion, so it could label idle measurements as successful long-fire evidence. `runFiringPerformance` also appended its record internally while callers appended the returned record, duplicating desktop and mobile rows.

4. **P2 — CPU geometry is regenerated in fixed ticks and again at the render edge.** The initial adapter calls `projectileVisuals.draw(1)` from the fixed-tick `_draw`, then `syncVisuals(alpha)` from the real render path. A normal 60 Hz frame builds the new mesh twice; a 30 Hz render frame generally builds it three times. The discarded intermediate mesh builds are expensive arithmetic and buffer writes. Draw-call count alone does not expose this cost.

5. **P2 — Explicit transient arrays remain in the new render hot path.** The initial `projectileVisualKind` uses an array literal for Shooter-family membership and `_drawRound` uses another array literal for sphere-kind membership. These should be hoisted or replaced with scalar comparisons; claiming no per-frame allocations from typed-buffer reuse alone is insufficient.

6. **P2 — Some purported production fixtures omit the new final adapter.** `patches/splatoon3/tests/source-fixture.mjs::adaptProduction` and `scripts/weapons-fixture.mjs` initially hard-code the previous adapter chain. A test using `productionComposition:true` does not thereby exercise the new renderer. New subject tests must use the actual shared `adaptBuildSource`, assert the installed visual runtime, or read a native emitted build.

7. **P1 — New Three resource UUIDs perturb the shared gameplay PRNG at startup.** Three's `generateUUID` uses four `Math.random()` calls. New BufferGeometry, MeshPhysicalMaterial and Mesh objects consumed twelve additional draws. A matched native VM fixture with the deterministic stream installed before module load reproduced baseline initialization 128 draws versus new initialization 140 draws; first Shooter seed changed from `0.39488261798396707` to `0.2023443109355867`, and its x launch velocity changed from approximately `-0.02579434` to `-0.00034498`. Resetting the stream after constructor invocation hides this regression. Cosmetic resource construction must isolate its UUID randomness or otherwise preserve the startup stream.
