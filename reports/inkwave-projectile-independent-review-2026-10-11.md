## Initial findings

1. **P1 — Standard horizontal Roller never creates the intended liquid bridges.** `runtime/projectile-visuals.mjs::_rollerLinks` treats `fidelityRollerUnitIndex` as a per-glob adjacency index. The twelve native wide-swing globs all have source unit index zero; only the nearest unit has index one. The check `Math.abs(pi-qi)!==1` therefore discards every adjacent main-unit pair. A full composition, actual `Projectiles.fireFlick`, fixed random 0.5, two 60 Hz updates reproduced 13 bodies, 2,028 vertices, and `linkedRollerPairs=0`. Adjacent main heads were approximately 0.265 world units apart, inside the configured bridge interval of 0.18–0.9 at radius 0.3. This is a visible functional omission in the requested connected membrane.

2. **P2 — Coarse native update intervals mislabel history positions.** `recordStep` reads the final `p.prev` after `_step` returns. Native `InkFlightRuntime.stepHead` can execute multiple internal 60 Hz steps and overwrite `prev` on each. A real Shooter with `Projectiles.update(1/30)` recorded history age zero at z=2.565996 instead of its muzzle z=0.3; age 1/60 was z=3.698994 instead of the actual first endpoint z=2.565996; only the final age 2/60 endpoint z=4.831992 was correct. Menu-attract budgeting legitimately supplies coarse intervals. A history derived from the last segment is not a complete authoritative trajectory.

3. **P1 — The proposed long-firing browser performance capture measures a frozen game.** `scripts/check-inkwave-projectile-visuals.mjs::openGameContext` calls `g.debug.freeze()`, but the initial `runFiringPerformance` never unfreezes. Native `Game._loop` returns immediately while frozen. The independent rAF sampler can produce timestamps even while game-frame/projectile/render sample arrays remain empty. The harness initially had no nonzero native frame/shot assertion, so it could label idle measurements as successful long-fire evidence. `runFiringPerformance` also appended its record internally while callers appended the returned record, duplicating desktop and mobile rows.

4. **P2 — CPU geometry is regenerated in fixed ticks and again at the render edge.** The initial adapter calls `projectileVisuals.draw(1)` from the fixed-tick `_draw`, then `syncVisuals(alpha)` from the real render path. A normal 60 Hz frame builds the new mesh twice; a 30 Hz render frame generally builds it three times. The discarded intermediate mesh builds are expensive arithmetic and buffer writes. Draw-call count alone does not expose this cost.

5. **P2 — Explicit transient arrays remain in the new render hot path.** The initial `projectileVisualKind` uses an array literal for Shooter-family membership and `_drawRound` uses another array literal for sphere-kind membership. These should be hoisted or replaced with scalar comparisons; claiming no per-frame allocations from typed-buffer reuse alone is insufficient.

6. **P2 — Some purported production fixtures omit the new final adapter.** `patches/splatoon3/tests/source-fixture.mjs::adaptProduction` and `scripts/weapons-fixture.mjs` initially hard-code the previous adapter chain. A test using `productionComposition:true` does not thereby exercise the new renderer. New subject tests must use the actual shared `adaptBuildSource`, assert the installed visual runtime, or read a native emitted build.

7. **P1 — New Three resource UUIDs perturb the shared gameplay PRNG at startup.** Three's `generateUUID` uses four `Math.random()` calls. New BufferGeometry, MeshPhysicalMaterial and Mesh objects consumed twelve additional draws. A matched native VM fixture with the deterministic stream installed before module load reproduced baseline initialization 128 draws versus new initialization 140 draws; first Shooter seed changed from `0.39488261798396707` to `0.2023443109355867`, and its x launch velocity changed from approximately `-0.02579434` to `-0.00034498`. Resetting the stream after constructor invocation hides this regression. Cosmetic resource construction must isolate its UUID randomness or otherwise preserve the startup stream.

## Performance revision review

- The performance revision caches arithmetic intrinsics and fixed shape envelopes, directly addresses the history's approximate 60 Hz bracket with correction for irregular samples, reuses each ring's direction and normal scale, and caches uniform color per generated body slot. It retains 13 rings, 12 section vertices, all source radii/tail choices, shape coefficients and the existing fixed-capacity buffers. The new tables are module initialization storage; no explicit collection, vector, buffer or callback allocation was introduced in the render/history hot paths. A source review cannot substitute for allocation profiling in the actual browser.
- **P2 found and corrected — pending GPU color ranges were lost across multiple visual sync calls.** After a prior upload of red/blue slots, changing slot zero to green queued `[start=0,count=468]`; changing slot one to yellow in a second draw before upload replaced it with `[468,468]`. An emulated upload then left GPU slot zero red while its CPU/cache value was green. This can occur when render is skipped between sync calls. The final revision unions new dirty bounds with still-pending `color.updateRanges` using the same range record; Three clears consumed ranges after upload. Independent recheck produced `[0,936]` and matching green/yellow CPU/GPU slots. An unchanged subsequent draw neither increments the color attribute version nor adds an update range.
- **P2 found and corrected — direct history addressing changed exact-grid tangents.** The prior scan chooses the incoming segment at an interior knot, including its EPS boundary. The initial optimization instead selected the outgoing segment. For positions `0,0.001,1,2` at successive 60 Hz samples with velocity 10, sampling the first interior knot changed its limited tangent from approximately 0.127279 to 10. The final bracket backs up while `lowerAge >= sampleAge - EPS`, preserving the incoming segment. Independent exact-knot and nearby EPS-boundary samples now agree with the prior implementation.
- Independently compared optimized runtime `df569d8a…` with the pre-optimization implementation from commit `de230d56`: **500 body cases across all ten generated modes**, varying source-scale radius, trajectory interval and fractional timing, produced identical Float32 position and normal buffers, with no nonfinite values. A separate 200-case elliptical/circular ring-normal comparison also produced identical Float32 geometry, with normal-length error below `4.6e-8`. These comparisons cover the performance revision before the intentional endpoint-cap geometry change; they validate preservation of INKWAVE's procedural geometry, not Nintendo mesh parity.
- Timing denominators must be explicit. The initial old-stream “700-body” workload rendered only 139 primary heads plus 556 decorative satellites because of its instance cap; it cannot be compared as 700 primary heads against the new backend. A head-only baseline near the same cap (695 heads), frozen source SHA, runtime realm, warm-up and sample count are necessary for a useful CPU comparison. The reconstruction report records separate frozen VM/host measurements; these are buffer-generation timings, not real browser FPS, GPU timings or a native Android result. The final two semantic fixes require their final SHA to be identified separately from the earlier timed `406c2026…` snapshot.

## Final collision/capture harness inspection

The inspected final script `scripts/check-inkwave-projectile-visuals.mjs` (SHA-256 `c0163d1fffd936143df42f99e7cfa27fc728bfcda454194b58675c39a5b97eca`) uses the production Actor controller for the wall scenario rather than depending on the catalog's private `finishContact` hook. Its `_step` context records the actual `InkFlightRuntime.world` return before later effects can overwrite the reusable Hit. Admission requires that this same step newly creates `fidelityWallDrop`, has frame zero and is not done, places both `p.pos` and `p.prev` at `hit.point + normal * 0.025` within 0.003 world units, and matches a live, solid, exposed, planar stage face plus the configured wall block/face/normal. Native InkFlight executes one world sweep in each of these 1/60-second fixture steps. A standalone setup ray, detached-drop sweep or retirement without that transition does not satisfy the wall gate.

The floor scenario requires retirement following `Projectiles._impact` on a valid upward live-stage face. The Hit is copied before invoking the original method. Paint receipts and `_cpuSplat` face IDs are scoped specifically to that original impact call, and the gate requires an impact splat center within 0.02 of the production `hit.point + normal * 0.14` center plus CPU painting of the same hit face. It therefore does not accept a sibling's floor paint or a generic trail query as the head's terminal contact. Wrappers preserve original return values, restore nested step/paint contexts with `finally`, and are confined to the capture page. Frozen-match screenshot renders explicitly request a shadow refresh and reset renderer.info; shadow-consumption state is stored in receipts. Projectile-follow camera distance is bounded from recorded head positions and imported visual radius, and visible head projection/crop is required. The last twelve flight rows and attempts remain available on failure.

No P1/P2 defect was found in these contact admission gates by source inspection. This resolves the known observer gap in code, not by a successful final CI receipt. Two evidence metadata issues were reported and corrected by the parent: birth routes now test `p.inkProfile`, the actual native InkFlight authority, and impact receipts store `captureFrame`/`elapsedSinceImpactFrames` with filenames distinguishing contact from post-contact capture. The camera receipt also separates raw `sourceDrawRadius` from `calibratedHeadRadius`, and bounds use the latter. The corrected script passes `node --check`. These label fixes do not change projectile integration or the contact admission gate.
