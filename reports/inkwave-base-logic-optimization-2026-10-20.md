# 基底ロジックの見直しとモーション計算の最適化（2026-10-20）

基準: `eb65d48d2870ee92b8080f5261d185f7b9a28602`（`main`）。計測スクリプトは [`inkwave-base-logic-optimization-2026-10-20/`](inkwave-base-logic-optimization-2026-10-20/)。

## 何を見たか

本番合成ビルド（`_site`）を Chromium 141 / ANGLE SwiftShader で起動し、Tidewater のナワバリ（8人・7bot、LOW、描画なし）を固定 1/60 秒で進めて CPU プロファイルを取った。

| 範囲 | 1フレームあたり（基準） | 内訳 |
| --- | --- | --- |
| シミュレーション全体 | 平均 10.5 ms、p95 18.2 ms | 固定60Hz tick と HUD |
| `Character.update` | シミュレーションの 53% | クリップ標本化・FK 21%、リターゲット・接地 18%、武器姿勢 5% |
| three.js `updateWorldMatrix` | 7% | 大半がリターゲット内のキャラクター全体更新 |
| HUD | 4% | 体力バー・チーム集計 |

1 tick・1体あたり、クリップ標本化 6.9 回（すべて全骨 FK 付き）、FK 10 回、補間 10 回、曲線評価 443 本、キャラクター全体の行列更新 5.2 回（1回 約150ノード）。骨66本のうち、1クリップで回転が動くのは約30本だった。

描画込みのプロファイルは SwiftShader の GL 呼び出し（`uniformMatrix4fv` など）が 92% を占め、実 GPU の描画 CPU コストの判断材料にならないため、今回の最適化対象から外した。

## 変更

すべて、計算結果をビット単位で変えない変更に限った。歩行・泳ぎ・射撃・塗り・接地の数値や判定は変えていない。

### 1. `source-bank.js` を直接ソース化

`inkwave-public/src/game/motion/source-bank.js` に、これまで4つのアダプター（`pose-rotation-adapter.mjs` は削除）が加えていた5つの書き換えを取り込み、ビルド時の書き換えをなくした。移行直前の本番合成結果は `patches/local-quality/tests/fixtures/source-bank-composed-before-direct-migration.mjs.txt` に固定し、比較の基準にだけ使う。

同じファイルで、次の計算を削った。

- **曲線のキー区間ヒント**: 出力ポーズごと・クリップごとに、前回の区間番号を覚える。二分探索が選ぶ区間と完全に同じ区間だと確認できたときだけ使う（キーが単調でない曲線は常に二分探索）。
- **動かない回転の事前計算**: クリップの曲線が回転を書かない骨の四元数は、クリップの基準姿勢から一度だけ同じ式で求める。
- **FK の展開**: `Matrix4.compose`、`multiplyMatrices`、`Quaternion.multiply`、`normalize` と同じ演算を同じ順序で書き下した（符号付きゼロ・正規化の扱いも同じ）。
- **先頭の骨だけの FK・コピー・補間**: `fk(count)`、`copy(other, count)`、`mix(other, weight, count)`。親が子より前に並ぶバンクだけで有効になり、それ以外や数値でない引数は全骨。

### 2. 読まれない FK の範囲を絞る（`motion-fk-hotpath-adapter.mjs`）

- 歩行の各クリップ・待機・特殊状態の標本化では、FK の結果を読むのは脚の目標、足・つま先の高さ、頭基準の髪の揺れだけで、その後に全骨の FK が必ず走る。この標本化の FK を 66 骨から先頭 30 骨に絞った。
- 体のバランスの中心ポーズは、ワールド回転を腰〜頭の22骨しか読まない。短歩幅（弱入力）の休止歩容と混ぜる場合を除き、局所姿勢の補間もこの範囲に絞った。休止歩容の FK は脚の16骨。

### 3. キャラクター全体の行列更新の重複をなくす（同アダプター）

`retarget.apply()` は最後にキャラクター本体の部分木を更新し、直後の `ground()`（旋回中は `protectTurningFeet()`）が冒頭でルート以下を再び全部更新していた。間に変わるのは出現時のクロスフェードだけなので、その場合は従来どおり全部更新し、それ以外は本体の部分木を更新し直さない（ルート・祖先・本体以外の子は更新する）。

## 基底ロジックのレビュー所見（変更なし）

### 固定クロックは経過時間を捨てない

`patches/splatoon3/runtime/clock.mjs` の固定60Hzクロックは、1フレームで最大240 tick まで追いつき、それを超えた時間も次フレームへ持ち越す。`main.js` の `dt = Math.min(dt, 1 / 24)` は `splatoon3/adapter.mjs` が除去している。180秒が各フレームレートで10,800 tick になることは `patches/splatoon3/tests/clock.test.mjs` が保証しており、設計どおりの挙動と判断した。

INKWAVE は実時間に追いつこうとする。本家が処理落ち時に追いつくのか、進行ごと遅くなるのかは公式資料で確認できず、未確認。1 tick の処理が 16.7 ms を超える端末では持ち越しが増え続け、1フレームの tick 数が上限まで増える可能性がある（「## 計測」の CPU 制限下の測定を参照）。

`patches/local-quality/intermediate-tick-budget.mjs` のコメントは「時計の1/24秒クランプで合計 dt は0.1秒よりずっと小さい」としているが、このクランプはもうない。100 ms を超える停止の後は、bot の `Character.update` に渡る合計 dt がネイティブの0.1秒上限で切られ、表示用のばね・平滑化の時間が失われる（ゲーム進行には影響しない）。

### ブラウザでの再現性

乱数を固定し、rAF・タイマーのコールバックを別系列の乱数にし、計測フレームの `performance.now` を仮想時計にしても、ページを読み直すと導入演出中の bot の動きが変わった。開始直後の状態は一致しており、原因は特定できていない。bot を止めてローカルプレイヤーだけを固定入力で動かす比較は「## 計測」に記載する。

## スプラトゥーン3との比較の範囲

ポーズの計算量を減らしただけで、移動・加速・停止・旋回・射撃・塗り・インク・接地の軌道・アニメーション係数・リターゲットの係数は変えていない。挙動比較記録の未確認項目はそのまま残る。ロジック単体・Node の実キャラクター・ブラウザの比較は、本家の実機比較の代わりにならない。
