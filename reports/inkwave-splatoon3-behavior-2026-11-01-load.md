# 2026-11-01 追記: ネイティブステージの負荷（続き）

本家の挙動との差分ではなく、Web上の描画・CPU負荷の改善記録。

- **画面サイズ読み取りのキャッシュ**（`patches/local-quality/viewport-cache.mjs`）
  - HUD、照準と自分の体の重なり判定（self-occlusion）などは、毎フレーム `innerWidth` / `innerHeight` を読む。スタイルを書き換えた直後に読むため、そのたびにブラウザがレイアウトを計算し直していた。
  - 画面サイズが変わったとき（resize / orientationchange / visualViewport の resize）だけ値を更新するようにした。
  - 測定条件: humpback / ナワバリ / iPad プロファイル / 描画なし / 300 フレーム。
  - 結果: 1 フレームあたり、HUD ミニマップで約 1.3 ms、self-occlusion で約 1.7 ms のレイアウト再計算がなくなった。ページエラーは 0。
- **変換済みステージデータ（`native-prebuilt/`）の作り直し**: 未実施。理由は次の 2 つ。
  - 作り直しに必要な basisu v1.16.4（npm `basis_universal@1.16.4-1` に同梱されているバイナリ）の実行が、このセッションの権限で止められた。
  - 本番の Pages ワークフロー（`.github/workflows/pages-inkwave.yml`）は、sparse-checkout で `native-prebuilt/` を取得していない。作り直しても、それだけでは本番に反映されない。データは全体で約 1.49 GB（配列 913 MB、色パック 323 MB、詳細パック 250 MB）あり、Pages の公開サイズ上限（1 GB）と Git LFS の転送量も問題になる。

## 2026-11-02 追記: ネイティブステージの色テクスチャを圧縮形式で配信

- **原因1: 圧縮テクスチャの展開が止まっていた**
  - 同梱の Basis transcoder は、関数を文字列から生成する処理（embind の `new Function`）を使っていた。ページの CSP は `'unsafe-eval'` を許可していないため、KTX2 の展開ワーカー内でこの処理が失敗していた。
  - 結果として、KTX2 の展開はすべて応答を返さないまま止まっていた。既存の「変換済みデータを全部使う経路」も同じ状態だった。
  - 文字列から生成していた呼び出し部分を、文字列を使わない関数（クロージャ）に置き換えた。
  - 確認: 25 枚 × BC7 / ASTC / ETC1 × 全ミップマップで、展開結果が修正前とバイト単位で一致。
- **原因2: 変換済みデータが stale で使われていなかった**
  - `native-prebuilt` の形状データは、変換コードとの整合が取れておらず（stale）、採用されていなかった。
  - ただし色パックは、画像処理ツールと固定した原典だけで決まる。humpback を作り直したところ、パックも対応表も既存のものと一致した。
  - そこで、ビルド時に色テクスチャの対応表だけを採用し、ブラウザ内の形状変換と組み合わせるようにした。
  - GPU が圧縮形式に対応していない環境では、これまでどおり PNG を使う。
- **測定**（humpback / iPad プロファイル / SwiftShader）
  - ステージのテクスチャ 63 枚すべてが圧縮形式になり、合計約 20 MB。
  - 同じ解像度の RGBA8 なら約 80 MB になる（推定）。GPU 上のテクスチャ量は約 1/4。
  - ステージ準備は、40 秒時点の進捗で比べると、圧縮なし 26% → 圧縮あり 53%。
- **配信**: Pages は stage.json と色パックだけを LFS から取得する（取得内容はキャッシュする）。サイトは 136 MB → 約 444 MB。
- **未確認**: 物理 iPad での fps とメモリ。
